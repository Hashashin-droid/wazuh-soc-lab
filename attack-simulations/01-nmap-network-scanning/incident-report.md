### 3. Technical Analysis

#### 3.1 Host Discovery

##### 3.1.1 Overview

In Stage 1 of the attack simulation, `nmap -sn` was used to discover active hosts on the target network. No alerts were generated by Suricata and forwarded to Wazuh because `-sn` option uses ARP broadcast requests for host discovery. 

##### 3.1.2 Detection Gap

Suricata did not generate alerts for ARP-based host discovery because ARP protocol operates at Layer 2 of TCP/IP. Suricata operates primarily at Layer 3 and above. Although Suricata can log ARP events in its EVE JSON output, standard Suricata signature rules do not inspect or trigger alerts on Layer 2 Ethernet headers

#### 3.2 Half-open TCP SYN Scanning with Service Version Detection

##### 3.2.1 Overview

In Stage 2, Nmap was executed using `nmap -sS -sV -T3` to identify open TCP ports and fingerprint the services running on the target host. The `-sS` option performs a half-open TCP SYN scan by sending SYN packets to the target ports. An open port typically responds with SYN-ACK, while a closed port responds with RST. This allows Nmap to determine port states without completing the full TCP three-way handshake during the initial scan.

The `-sV` option performs service version detection by sending additional, protocol-specific probes to discovered open ports. By analyzing the responses, Nmap attempts to identify the services and, where possible, their software versions. The `-T3` option uses Nmap's normal timing template, balancing scan speed and reliability.

The scan identified four open TCP ports:
- **Port 135 (MSRPC):** Used by Microsoft Remote Procedure Call (RPC), which enables processes to communicate with services on the same or remote systems. Exposure may provide information about available RPC services and Windows system functionality.
- **Port 139 (NetBIOS-SSN):** Used by NetBIOS Session Service, traditionally supporting session-based communication and file or printer sharing over NetBIOS.
- **Port 445 (SMB):** Used by Server Message Block (SMB) for network file sharing, printer sharing, and other Windows network services. This port warrants particular attention because exposed SMB services can be targeted through misconfigurations, weak credentials, or unpatched vulnerabilities.
- **Port 5357 (WSDAPI):** Commonly associated with Web Services for Devices (WSD), which supports device discovery and communication on Windows networks. Its exposure may reveal additional information about Windows services and device functionality.
    
The remaining 996 TCP ports responded with TCP reset (RST) packets, indicating that they were closed at the time of the scan. This means the target was reachable on those ports but did not have listening TCP services accepting connections.

##### 3.2.3 Detection Gap

Although the TCP SYN scan and service enumeration identified four open ports (135, 139, 445, and 5357), Suricata did not necessarily generate a dedicated port-scan alert for the entire scanning activity. The existing rules may detect specific protocol patterns or suspicious connections without correlating repeated SYN probes across multiple destination ports

##### 3.2.4 Triage Reasoning

- **Reconnaissance pattern:** Alerts involving multiple unrelated services, including databases, VNC, RDP, and Java RMI, originating from the same source within three minutes suggest automated service enumeration rather than a targeted exploitation attempt. The activity is consistent with Nmap service version detection (`-sV`).
- **Potential false positives:** The `ET POLICY ... Likely Malware` alerts may be triggered by protocol-specific probes generated during Nmap's service detection phase. These signatures do not independently confirm malware activity. The alerts should be correlated with the source IP, timestamps, destination ports, and scan activity before determining whether escalation is necessary.

### 4. Recommended Remediation Actions

#### 4.1 Detection Improvements

1. Add a correlation rule that raises severity when one source triggers many Suricata alerts in a short window

2. Add ARP monitoring (e.g., arpwatch) to cover ARP-based host discovery

#### 4.2 Response actions (if these were real)

1. **Validate the Activity:** Correlate Suricata alerts with Wazuh logs, source and destination IP addresses, timestamps, and destination ports to confirm whether the activity is consistent with Nmap service enumeration.
2. **Identify the Source:** Investigate the originating host, its owner, network location, and recent activity. Review firewall logs, endpoint telemetry, and authentication records for additional suspicious behavior.
3. **Assess the Exposed Services:** Review TCP ports 135 (MSRPC), 139 (NetBIOS-SSN), 445 (SMB), and 5357 (WSDAPI). Confirm whether these services are required, restrict unnecessary exposure, and verify that applicable security patches and configurations are up to date.


### 5. Lessons Learned

- **What Worked:** The Suricata-to-Wazuh integration generated alerts for some activities during the scan, with timestamps that helped correlate events with the attack simulation. This demonstrated the value of centralized security monitoring.
- **What Didn't Work:** ARP-based host discovery was not detected by the current configuration. Additionally, the 33 individual Level 3 alerts could be difficult to identify as a single reconnaissance event in a high-volume SOC environment, highlighting the need for correlation-based detection and alert prioritization.
- **Triage Takeaway:** IDS alert signatures can be misleading when viewed in isolation. Analysts should correlate timestamps, source and destination IP addresses, destination ports, and the originating activity before classifying an event as malicious or escalating it as a potential malware incident.
